## ガイド例

### 例 1 — 頻度・次数・更新回数を閾値でheavy/lightに分け、両側の計算量を均衡させる。その発動条件、正当性、計算量を説明し、未知問へ実装できる

題材: [ABC219 G「Propagation」](https://atcoder.jp/contests/abc219/tasks/abc219_g)

#### このOutcomeを支える根拠

- 高次数頂点からの上書き broadcast を次数平方分割と timestamp 付き pull に変え、query を処理できる。

#### 観察

- 一回の query は中心 x の現在値を全近傍へ上書きするため、次数の大きい頂点が何度も選ばれると隣接リスト走査の総量が大きくなる。一方、次数 B 以上の頂点数は次数和から高々 2M/B 個である。
- 更新は加算ではなく代入なので、各頂点の正しい値は自分へ届いた更新のうち時刻が最大の一つだけで決まる。高次数頂点からの配布は、その頂点に値と時刻の看板を残して遅延できる。

#### 候補を比較する

- **採用**: 次数 B 未満の query は全近傍へ即時反映し、次数 B 以上なら看板だけを更新する。頂点の値が必要な時に隣接する高次数頂点の看板から最新時刻を解決する。 — 軽頂点の隣接走査を B 未満に抑え、遅延更新の確認先も高次数頂点数以下に抑えることで、疎グラフの次数和を利用できる。
- **棄却**: 全 query で x の隣接頂点を列挙して値を書き換える。 — 星型などで中心が繰り返し指定されると、一回 Θ(N) の更新が Q 回発生する。

#### 鍵となる着眼

- 頂点 v を参照する直前に、v の明示値の時刻と v に隣接する全 heavy 頂点の看板時刻を比較すれば、未配布の代入を含む現在値を復元できる。

#### アルゴリズムへ接続する

閾値 B を √M 程度に置き、各頂点について隣接 heavy 頂点を前計算する。query x の先頭で x を最新化し、x が light なら全近傍の値・時刻を更新、heavy なら x の看板へ値・時刻を保存する。全 query 後も各頂点を同じ方法で最新化して出力する。


## 転用するときの確認

- **次数平方分割**: グラフ query の一回の費用が中心頂点の次数に比例し、辺数の総和だけが小さいとき。 適用: 低次数は push、高次数は lazy にし、閾値 B と heavy 頂点数 M/B の釣り合いを取る。
- **timestamp による遅延代入**: 複数の上書き更新が競合し、最も新しい更新だけを採用すればよいとき。 適用: 値と query index を組で保存し、参照時に最大 timestamp の候補を選ぶ。
- 高次数からの broadcast が重いとき、更新を発信者に置き、必要時に受信者が少数の重い発信者だけを pull できないか考える。
- heavy 中心が看板を立てた直後に、その隣の light 頂点が発信者になる例を追い、「発信前の resolve」が必要な箇所を確認する。
